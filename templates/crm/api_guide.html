Integration guide

Executive CRM API

Existing outreach endpoints and tokens remain compatible. Executive handoff is explicit; the old founder-escalation flag does not create a CRM lead.

Authentication and permissions

Use Authorization: Bearer <access_token> and Content-Type: application/json. Executives can read all CRM leads and opportunities, but update only their assigned records. Managers and system administrators can edit and reassign. Outreach users can read their own handoffs but cannot edit CRM follow-up. Only sales interns, inside sales and managers may submit new leads.

Submit a lead

Required: company_name (200 characters), contact_name (200), context (5,000), assigned_to (active executive user ID), and at least one of contact_email (254), contact_phone (50) or contact_linkedin_url (500). Optional: website (500), location (200), contact_title (200). A manager must provide workstream: intern or inside_sales; other users' workstream comes from their role. Duplicate companies in a channel must be handed off from the existing prospect.

POST /api/v1/crm/leads/
{"company_name":"Example Advisory","contact_name":"Asha Rao",
 "contact_email":"asha@example.com","assigned_to":12,
 "context":"Requested a discovery call about a GCC team."}

Handoff an existing prospect

Send assigned_to (integer) and context (up to 5,000 characters). LinkedIn also requires response_confirmed: true, meaning an actual client reply was received. An unassigned prospect must first be claimed. Repeating a handoff returns the same lead without changing its assignment. Historical migration is administrator-reviewed in the browser, not exposed as a bulk API.

Update executive follow-up

PATCH requires the integer version from the latest GET and at least one changed field. Fields: status, next_action (250), next_action_date (YYYY-MM-DD), discovery_at (ISO 8601 timestamp with offset), discovery_timezone (IANA name, 80), discovery_outcome (3,000), drop_reason (2,000), comment (5,000). Managers can also send assigned_to. Set action and date together; a scheduled meeting needs time and zone; completed discovery needs an outcome; dropping needs a reason. Converted leads are updated through their sales opportunity.

Statuses: {% for value, label in statuses %}{{ value }} ({{ label }}){% if not forloop.last %}, {% endif %}{% endfor %}. converted is set by conversion, never PATCH.

PATCH /api/v1/crm/leads/23/
{"version":1,"status":"discovery_scheduled",
 "discovery_at":"2026-10-20T09:00:00-05:00",
 "discovery_timezone":"America/Chicago",
 "next_action":"Run discovery","next_action_date":"2026-10-20"}

Convert and manage a sales opportunity

Conversion requires name (200), requirements (5,000), stage, probability (integer 0–100) and decision_note (2,000). Optional fields: estimated_value (nonnegative decimal, up to 13 integer digits and 2 decimal places), currency (three letters, required with value), expected_close_date, next_action (250), next_action_date, closure_reason (2,000), comment (5,000). Managers may reassign with assigned_to. Value may remain unknown. Repeated conversion returns the same opportunity. Reopen a dropped lead before converting it.

Stages: {% for value, label in stages %}{{ value }} ({{ label }}){% if not forloop.last %}, {% endif %}{% endfor %}. New opportunities cannot start won/lost. Opportunity PATCH supports the same fields except decision_note, and requires version. Won/lost requires closure_reason, sets closed_at and normalizes probability to 100/0. Reopening clears closed_at.

POST /api/v1/crm/leads/23/convert/
{"name":"Example GCC engagement","requirements":"Build a team",
 "stage":"qualified","probability":25,"estimated_value":"25000.00",
 "currency":"USD","decision_note":"Discovery confirmed fit."}

Comments, lists and errors

Post {"comment":"Meeting confirmed."} to append a comment. Comments and changes are append-only, with actor and timestamp. Lists return count, page, pages, results; page size is 25. Filters: search, assigned_to, source_channel, status (lead status or opportunity stage), due (today/overdue/upcoming/none), date_from/date_to (escalation date), and close_from/close_to (opportunities only). Date filters use YYYY-MM-DD. Due filters exclude terminal records. Unknown historical escalation dates remain null and do not match date ranges.

GET returns source contact details, ownership, version and timestamps; monetary values are decimal strings. PATCH preserves omitted fields. Blank optional fields can be cleared with null or an empty string. Unsupported fields and invalid types are rejected: 400 validation, 401 missing/invalid token, 403 permission denied, 404 not visible/not found, 409 stale version. Errors contain error and, for field validation, field_errors. No email, calendar event or external message is sent by these endpoints.
