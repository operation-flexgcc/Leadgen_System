Authentication and existing APIs

Use the same token until you choose to revoke it.

Authentication

Send the token in every request. New tokens do not need refresh tokens.

Authorization: Bearer <access_token>

Existing refresh tokens

If you still have a refresh token generated under the old system, exchange it once for a persistent access token:

POST /api/v1/token/refresh/
Content-Type: application/json

{"refresh_token":"<old_refresh_token>"}

Update company details

Managers can update any company. Outreach users must first claim the matching prospect in their user class.

PATCH /api/v1/companies/<company_id>/
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "short_description": "...",
  "consulting_focus": "...",
  "client_segment": "...",
  "eligibility_evidence": "...",
  "contact_name": "...",
  "contact_title": "...",
  "linkedin_url": "https://www.linkedin.com/in/...",
  "email": "optional@example.com",
  "phone": "+1 ..."
}

General prospect workflow endpoint

The existing general endpoint remains available for backward compatibility. New integrations should use the four purpose-specific APIs above so unsupported fields fail fast within the relevant workflow section.

PATCH /api/v1/prospects/<prospect_id>/
Authorization: Bearer <access_token>
Content-Type: application/json

Use the prospect ID returned by the claim endpoint or listed in the company response. Managers and system administrators can access any prospect. Frontline outreach users must own the exact prospect.

Claim a prospect

POST /api/v1/companies/<company_id>/claim/
Authorization: Bearer <access_token>

The response includes the prospect ID needed for workflow updates. If another outreach user has already claimed it, the API returns HTTP 409 and that user's name.
